# Guarded Shipment writes

Proposed sandbox proof for the worker's USPS `Delivered` transition. The current `sync_delivered` workflow returns status proposals for allowlisted Shipments and rejects `apply=True` before accessing either connector. `SalesforceClient.update_statuses` sends IDs and new status values to sObject Collections. Its request carries no snapshot of the fields that made a shipment eligible. Conditional GETs on the authorized fixture returned HTTP 200 with both older and future dates. The prior checks did not establish header propagation or conditional PATCH behavior.

## Salesforce options

| Option | Competing writers and same-second changes | Decision |
| --- | --- | --- |
| sObject Rows `If-Match` | Salesforce documents ETag matching for Account records only. | Exclude for Shipment. [Conditional Request Headers](https://developer.salesforce.com/docs/platform/api-rest/guide/intro-rest-conditional-requests.html) |
| sObject Rows `If-Unmodified-Since` | Salesforce classifies the condition as weak and accepts an HTTP date with second precision. A stale request returning 412 would establish one case. It would leave the behavior for two writes within a second unproven. | A narrow native diagnostic if needed. The documented contract does not establish the required same-second guard. [Update Records Using sObject Rows](https://developer.salesforce.com/docs/platform/api-rest/guide/resources-sobject-retrieve-patch.html) |
| sObject Collections, Composite and Composite Graph | Collections supports up to 200 records and per-record outcomes. Its documented payload has no per-row condition. Composite supports resource-specific headers on row subrequests and Graph references that subrequest format. Batching changes request count and rollback scope. The row condition remains timestamp-based and Graph header behavior for Shipment is unverified. | Retain Collections as the baseline for measuring batch behavior. Avoid treating batching or a separate re-read and PATCH as a concurrency guard. [Collections update](https://developer.salesforce.com/docs/platform/api-rest/guide/resources-composite-sobjects-collections-update.html), [Composite Request Body](https://developer.salesforce.com/docs/platform/api-rest/guide/requests-composite.html), [Composite Graph](https://developer.salesforce.com/docs/platform/api-rest/guide/resources-composite-graph.html) |
| Apex REST with a locking read and comparison in one transaction | `FOR UPDATE` reads the current row and locks it through the transaction. Comparing the current fields can detect an intervening change to a relevant value within the same second. A later writer with stale data can still overwrite the result after lock release. Salesforce also releases the Apex row lock on callout. | Verify the single-record case first. Keep the carrier lookup outside the Salesforce transaction. [Locking Statements](https://developer.salesforce.com/docs/platform/apex-dev/references/apex-dev/langcon-apex-locking-statements.html) |

## Smallest candidate

Use one authorized sandbox Shipment and a narrow Apex REST operation. The operation accepts the record ID and expected `OrderSummaryId`, `Provider`, `TrackingNumber` and `Status` from the same snapshot used for planning. Keep `Delivered` fixed as the only allowed target. A future worker must carry that snapshot from its read through the carrier lookup. The current dry-run result is only a status proposal and lacks those preconditions.

In one Salesforce transaction, look up the authorized Shipment by ID with `FOR UPDATE`, then compare its current fields with the expected values while the lock is held. Use case-sensitive string comparison for snapshot text, since Apex `==` compares strings without regard to case. Require USPS, a nonempty tracking number and a current status in `Created`, `Shipped` or `In Transit`. When the row matches and is eligible, change only `Status`. Return a conflict on mismatch without changing the row. Re-read after a known lock conflict and reconcile the observed state after an ambiguous timeout before deciding whether to plan again. [Apex Expression Operators](https://developer.salesforce.com/docs/platform/apex-dev/references/apex-dev/langcon-apex-expressions-operators-understanding.html), [Apex String methods](https://developer.salesforce.com/docs/platform/apex-ref/references/apex-ref/apex-methods-system-string.html)

Enforce record sharing and explicit user-mode query and DML under the scoped identity. Require access to the proof class and the minimum Shipment field permissions. Check server-side fixture scope as well as record access. An ID supplied by the caller or the simulation's source key does not confer authorization. Verify that the target org and Apex API version support the locking query and user-mode update on Shipment. [Exposing Data with Apex REST Web Service Methods](https://developer.salesforce.com/docs/platform/apex-dev/references/apex-dev/apex-rest-exposing-data.html), [Set an Access Mode for Database Operations](https://developer.salesforce.com/docs/platform/apex-dev/references/apex-dev/apex-classes-enforce-usermode.html)

This guard protects the worker from a change to the compared values that is visible when it acquires the lock. If another writer can restore all the expected values before the lock, the comparison cannot detect the intervening changes. If the business rule requires detecting every revision, including a change and reversal, evaluate a revision that advances on every relevant write. Establish which Salesforce users, flows and integrations can change the guarded fields, and whether they will share this protocol or follow an equivalent enforced rule. A successful proof of the worker's stale-write rejection does not protect its result from a subsequent unguarded writer.

## Minimum sandbox evidence

Use the documented disposable fixture setup. The proof requires authorization to deploy the temporary Apex operation and to perform scoped writes on labeled disposable Shipments. Use a scoped test identity plus an authorized competing writer, with an inaccessible or out-of-scope fixture for the permission check. Keep fixture IDs, the org URL and credentials in restricted project configuration. The scoped test session verifies the operation. Unattended worker authentication remains a separate dependency.

1. **Fresh snapshot.** Prove the authorized identity can write `Delivered` from a supported state. Read back the row and confirm the operation changed only the intended business field after any org automation.
2. **Stale snapshot and same-second change.** Take a snapshot as the worker, have the competing writer change one of the compared fields, then submit the stale snapshot. Verify the worker reports a conflict and preserves the competing change. Repeat with the fixture's baseline update and the competing change committed within the same second. Compare the recorded Salesforce modification times and actual ordering to establish the case. Test a tracking value changed only in case if the target field preserves it.
3. **Overlapping attempts.** Send two attempts from the same eligible snapshot with actual overlap. Confirm at most one applies and the other sees a fresh conflict or a reported lock failure. Exercise a known lock failure and an ambiguous response separately to check that neither path retries blindly.
4. **Scope and access.** Verify the allowed fixture succeeds under the scoped identity and an inaccessible or out-of-scope ID cannot be modified. Check field restrictions using the target permissions and keep response details limited to the caller's authorized records.

This is a one-record proof proposal. A later batch test must verify per-record correlation, partial failures and reconciliation, rollback behavior, related-record locks, and the five-request target under representative load. The existing Collections criterion needs reconciliation before adopting a different update API. The current evidence supports leaving automatic writes disabled. The offline checks cover that gate and the existing simulation, while the Salesforce concurrency and permission outcomes above still require the sandbox proof.
