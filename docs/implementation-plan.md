# Shipment tracking POC implementation plan

**Current POC:** Salesforce is the source of sample shipments; there is no ERP. A single authenticated USPS API lookup succeeded; recurring polling and Salesforce synchronization remain unverified. See the [current story](../story/user-story.md) for progress and acceptance.

**Goal:** Give authorized B2B buyers shipment status and tracking links associated with their orders, using twice-daily outbound synchronization. This design and execution plan has scoped evidence for the offline synthetic prototype. Live integration, deployment and acceptance remain pending.

**Approach:** Build on the existing middleware foundation. For this POC, read test Shipment records already in Salesforce, use USPS for the live carrier check, simulate UPS and FedEx, and write verified results back to Salesforce. Proposed carrier polling is 07:15 and 19:15 Eastern Time; no ERP or dispatch job is required. ERP ingestion is a deferred extension. Scheduling, daylight-saving and missed-run behavior remain to be verified.

**Configuration:** Environment variables or a local ignored config file supply Salesforce login URL and credentials, carrier credentials, API versions, schedule timezone, and operational settings. Commit only placeholder examples. Use the Salesforce instance URL returned by OAuth; never hard-code an environment hostname or embed credentials in source, docs, test fixtures, URLs, logs or Git history. Restrict actual files and inject secrets securely at runtime. A `.gitignore` is a guardrail, not a security boundary.

## Build and verification sequence

1. **Establish contracts (ERP parts deferred).** Identify the existing middleware, its supported connector versions, and the ERP endpoint, pagination and immutable package ID. Agree how its order reference maps uniquely to Salesforce and how tracking links are supplied. Describe target Shipment fields and verify write permissions, picklist API values and supported order relationship. If an Order-only fallback is unsupported, stop and document the gap. Preserve SAP ownership of fulfillment.
2. **Configure Salesforce sandbox (external-ID applicability to this POC is pending).** Verify Shipment access; create/validate a unique external ID suitable for a stable package identity. Stage requiredness so legacy records and other writers are not broken. Verify how a safe tracking URL is stored or generated on Shipment and how the chosen Salesforce API and storefront render it. Configure a dedicated integration user and least necessary access. Do not assume a particular sharing mechanism works without testing.
3. **Define canonical data and ledger (source cursor and ERP replay are deferred).** Define package identity, source version, order reference, carrier, tracking number, URL, status, dates and event time. Use a durable work ledger with source cursor, staged payload, per-record outcome and retry/quarantine state. Never log tokens or unnecessary sensitive data. Test duplicate source pages, identical timestamps and crash recovery; do not advance the cursor past data not durably staged.
4. **Deferred future extension — build dispatch job.** Read new and updated ERP packages in bounded pages; stage first, match exactly one order in the correct account/store, and quarantine unmatched or ambiguous packages. Upsert Salesforce Shipments by stable external package key in batches of up to 200. Inspect every result even if the HTTP response is successful; retry transient failures and retain permanent ones for correction. Reconcile uncertain timeouts without creating duplicates.
5. **Build carrier job.** Query eligible nonterminal shipments and follow Salesforce pagination. Poll USPS through its verified provider contract; use simulated UPS and FedEx results until live access is available. Define an approved versioned mapping per carrier; do not assume identical codes across carriers. Compare all owned status and date fields and update only changes in batches up to 200. Preserve carrier event time and prevent old events replacing newer ones; specify a correction and post-delivery policy. Unknown statuses are retained for review.
6. **Expose buyer tracking.** Verify whether supported standard storefront components can show each real Shipment and tracking link. Test a buyer with two shipments in different states, an order without shipments, stale data and an unauthorized account. Salesforce access governs record visibility; carrier link behavior is external. Document the supported alternative if standard configuration cannot meet this requirement.
7. **Operate and test.** For the POC, test the status schedule, duplicate replay, partial Salesforce results and carrier outage, 401/403/429/5xx, timeout after commit, older scans, mapping gaps and buyer isolation with synthetic data. Alert on failed SaveResults with a safe identifier, protected payload reference and error; choose an operator and destination. Record counts, retries and recovery. Do not trigger real carrier notifications or customer communications during tests.
8. **Measure API usage.** The requested target is at most five Salesforce REST requests per run for 800 active shipments: one unpaginated read plus four update batches. Pagination, retries, token handling, reconciliation and order lookups can exceed it. Record actual counts and resolve the accounting/exception policy; never drop shipments to meet the target.
9. **Prepare GitHub.** Review every proposed file and staged diff, scan for credentials, org-specific addresses, account identifiers and real shipment data, and check ignored files. Use a clean repository and synthetic examples. Verify repository owner and visibility before publication. If a secret is exposed, rotate it and follow the organization's incident and history-removal process; deleting a later commit is insufficient.

## QA for each implementation increment

Use the [story checklist](../story/user-story.md#execution-checklist) and [pinned QA rules](https://github.com/aispanda/Reusable-Delivery/blob/6013aedacbc1ee7c3aaee24459152ee5ff381eef/CODE-QUALITY.md). Plan behavior checks and affected failure paths before each increment. Run the repository check locally and in CI. Material changes go to a fresh reviewer after writer checks. Record the proposed revision, tested revision, runtime, result and findings. Reopen affected checks after repair. Keep the offline CI pilot, sandbox integration verification and human acceptance as separate results.

## POC decisions still needed

Live USPS app credentials and API behavior; approved carrier status mapping; Salesforce field and buyer-sharing capabilities; approved status mapping and correction policy; alert destination; timezone behavior on missed or overlapping runs; and acceptance owner. The tracking link and statuses are required outcomes; implementation method remains subject to target-org validation. Human acceptance and independent verification are pending.
